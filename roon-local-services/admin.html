Disambiguation during text generation

When enabled for a kind, its prompt asks the model to flag genuine ambiguity (a title that could refer to more than one truly distinct album/track/artist) instead of silently guessing. When that happens, the remote shows the candidates as a pick-list instead of the generated text -- picking one triggers a real second generation for that specific one, which IS cached normally. Costs a little extra on every request for an enabled kind (the added instruction), and roughly doubles the cost of the specific requests that do turn out ambiguous (two real calls instead of one). If none of these are checked, generation works exactly as it did before this feature existed.

Key normalization

Custom rules for matching "the same" album or track across slightly different spellings (a remaster tag, a live/remix suffix) so they share one cached result instead of generating separately. Never applied to artist names. Runs AFTER spacing/case/accent normalization (already applied to everything, not shown here) -- so writing "live" below also catches "Live" and "LIVE", and "remaster" also catches "remastered" as a plain substring.

Rows run in order, each on the result of the one before it -- every row gets a turn, not just the first one that matches. Within one row, its symbols (one per line) are tried in the order written; the first one that matches wins and that row is done. Leave "If following text contains" blank to always cut once the symbol is found at all.
